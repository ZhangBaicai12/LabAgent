# PFD 技术方案（required 补全）

> **前提声明**：本方案按「**全部业务内容均为运行期配置**」撰写。
> 有哪些流程、每个流程有哪些节点、节点按什么顺序推进、每个节点处理与产出什么数据、挂哪些脚本与工具 —— 这些全部是配置数据，不是代码，方案不做任何具体业务假设。
> 四节只回答：**机制怎么定**。

## 0. 设计基调

从需求里抽出十三条与业务语义无关的硬约束，后续所有选型都是它们的推论。前十条是方案的地基，P11–P13 是评审时从后文章节**回收**出来的约束 —— 它们本来就已在起作用，只是没进地基表。

**先分清两类，它们用法不同**：

| 类别 | 成员 | 在推论中的作用 |
|---|---|---|
| **判据**（能排除方案） | P1、P3、P7、P9 | 用来做选型决策，选完即失效 |
| **约束 / 护栏**（限定做法，不排除方案） | P2、P4、P5、P6、P8、P10、P11、P12、P13 | 决定实现细节，永久有效 |

**只有四条是选型判据**，其余九条是护栏。把护栏当判据用会出现"某框架不支持 X 所以不能用"这类无效论证（例：P2 对四个候选框架都成立，见 1.1）。

| # | 性质 | 含义 | 约束类型 |
|---|---|---|---|
| P1 | **流程与节点运行期可变** | 加流程、改顺序、换数据来源都**不改代码、不重启、不发版**；改版即生效，**对改版后新建的实体**生效，在途实体仍按其锁版配置跑完（4.6） | 功能 · 判据 |
| P2 | **数据不出内网** | 全部组件须可内网 / 离线部署，无外网强依赖 | 部署 · 护栏 |
| P3 | **Agent 写入面窄** | 只需少数几类介入，不需要通用 Agent 能力（反思 / 规划 / 多智能体协作） | 功能 · 判据（**假设，非既成事实**，见下方触发信号） |
| P4 | **人工是流程的一部分** | 流程必须在**声明的**确认点挂起，人工处理后恢复。一期单点确认，会签留二期（4.13） | 功能 · 护栏 |
| P5 | **算力预算固定且本地** | 只管**钱**：推理在本机算力内，预算封顶。注意本地推理除 token 成本外还有**常驻算力占用**（3.6） | 成本 · 护栏 |
| P6 | **执行资源既有语言已知** | 存量执行资源是 Python，故主栈取 Python、Worker 默认同栈。**注意：同语言不是防格式不一致的手段** —— 防格式不一致靠契约（2.2 输出 schema 准入、3.8 同类共用明细结构）；契约不绑定语言（2.1） | 工程 · 护栏 |
| P7 | **一人开发** | 依赖数量 = 维护成本，框架升级与版本碎片是真实成本。**这条是双刃的**：它同时约束"引入重框架"和"自研过多"（1.2 末） | 工程 · 判据 |
| P8 | **确定性部分必须确定性** | 编排与校验要可复算、延迟可预期。**范围要写清**：编排路径与校验结果**可复算**（硬要求）；**推理结论事后不可复现，本方案显式放弃复现、改用 src 清单 + 留痕兜底**（3.7、4.10） | 延迟 / 可复算 · 护栏 |
| P9 | **同一实体的同一环节会被多次推进** | 且必须区分**重试**（同一次尝试内重复提交）与**重做**（回退后返工）两种语义，故幂等键必须含 attempt（2.5）。并发窗口是本条的直接后果，不是附加假设 | 功能 · 判据 |
| P10 | **中枢可用性不依赖推理服务** | 推理是增强项，不是关键路径；推理挂了业务照常流转 | 架构 · 护栏 |
| P11 | **外部系统不可改造、多数无接口** | 上游系统按现状使用，能读则读，写入无接口时**只能产出数据包 + 待办**，动作留在授权方手里（2.3 第三层） | 集成 · 护栏 |
| P12 | **存量产物与存量脚本不迁移** | 复用现有共享存储与存量脚本，只做**元数据登记**，不做数据搬迁（1.4） | 部署 · 护栏 |
| P13 | **签字 / 授权类动作不可由模型代行** | 电子签名、目检判定、FA 裁决、客户系统写操作必须留人工确认，这是 4.8「写操作只有一个闸门入口」与 6.1「不做审批流」的真实依据 —— **依据是责任与合规，不是 P3 的技术判断** | 合规 · 护栏 |

#### 边界必须写在性质里，否则会被后续机制推翻

P1 与 4.6（实体锁版）、4.2（表达力限定）是**同一件事的三个面**：P1 承诺"改配置零重启"，4.6 决定"改版对在途实体无效"，4.2 决定"能改的只有节点序与绑定"。只写 P1 不写后面两条，评审会直接判"自相矛盾"。同理 P4 承诺挂起恢复，但一期只有单点确认（4.13）。

#### 假设类性质必须给触发重评信号

第 6 节六项都有触发信号，地基里的假设类性质也必须有，否则会把当前判断固化成教条：

| 性质 | 触发重评的信号 |
|---|---|
| **P3**（Agent 只需少数几类介入） | 出现**规则表达不了、且必须多步推理**的介入场景，且这类场景不是偶发（对应 1.5 的延后装策略，届时该场景单独引入 LangGraph） |
| **P7**（一人开发） | 出现第二名开发者，或单人维护出现持续积压 |
| **P1**（流程运行期可变） | 出现"必须作用于在途实体"且无法用覆盖层表达的需求（对应 6.2，此时要重评锁版而不是加通道） |

**P5 与 P8 必须分开**：P5 管「花多少钱」，P8 管「结果能不能复算、延迟能不能预期」。把它们混成一条会导致为了省钱而把确定性逻辑塞进模型，破坏 P8。

**一句话结论**：配置驱动业务编排（自研编译 + 确定性执行），通用 Agent 框架只用在"确实需要多步推理"的少数场景，绝大多数介入规则化。

### 0.1 一条贯穿全案的设计准则

> **进版本的是「业务规则的形状」，留运行时的是「业务规则的具体取值」与「实际发生的事实」。**

这条准则用来回答"某样东西该版本化还是该运行时可改"。第 6 节六个待确认项里有四个本质上是这个问题。

| 进版本（形状） | 留运行时（取值与事实） |
|---|---|
| 节点序、输入输出绑定、执行资源绑定、允许状态集合、是否允许跳过、契约**版本号与兼容区间** | 时限的具体数值、责任人归属与委托、契约的具体字段、实际发生时刻与录入时刻、线下数据标记 |

判据：**形状变了就是流程变了，流程变了要走发布；取值变了业务要立即生效，不需要走发布。** 两者混在一起，就会同时失去"改流程不发版"（P1）和"改阈值立即生效"。

一条容易漏的推论：**只有形状进版本，所以"形状要作用于在途实体"天然是例外事件**（6.2）。这解释了 4.6 为什么不给重绑定通道 —— 不是省事，是判据的直接结果。

## 1. 框架选择

### 1.1 从性质推导选型标准

不按业务比，按能力维度比。先把性质翻译成技术要求，再判定。

**只有判据类性质能排除方案**，护栏类性质只决定实现细节。逐行标注了这一点，避免"某框架不支持 X 所以不能用"的无效论证：

| 来源性质 | 类别 | 技术要求 | 判定 |
|---|---|---|---|
| **P1** | 判据 | ① 流程能用**数据**描述建图<br>② 改配置**零重启重编译**（含版本快照）<br>③ 多次尝试的 attempt 语义 | ① 四框架都能（都能用数据构造图）<br>② 需自研编译器，框架需重启进程<br>③ 需自研，框架不内建 |
| P3 | 判据 | 不需要通用 Agent 能力，依赖越轻越好 | LangChain / Qwen-Agent 不采用（过重） |
| P7 | 判据 | 依赖少、API 面稳定、无版本并存 | LangChain 不采用（API 三套并存） |
| P9 | 判据 | 幂等须容纳多次尝试 + 并发窗口防护 | 四框架均不内建；可**表达**（每次尝试一个线程），但语义归属业务层，自研可精确控制 |
| P2 | 护栏 | 无外网强依赖，可离线部署 | 四框架均满足，**不参与选型** |
| P4 | 护栏 | 状态可持久化、可在声明的确认点挂起恢复 | LangGraph 原生；其余需自建 |
| P5 | 护栏 | 推理走可换端点，成本按 token + 常驻算力核算 | 走 OpenAI 兼容端点，四者均可满足 |
| P6 | 护栏 | 主栈与存量脚本一致（Python） | 与框架选择无关，由后端栈决定 |
| P8 | 护栏 | 编排路径不经过模型 | 四者均可满足（取决于用法，非框架能力） |
| P10 | 护栏 | 编排层与推理层可独立部署与降级 | 需推理层走独立端点（与 P5 的解耦同源，但管的是可用性不是钱） |
| P11 | 护栏 | 外部系统无写接口时，只产出数据包 + 待办 | 与编排实现无关（2.3 第三层） |
| P12 | 护栏 | 复用现有共享存储，不搬迁存量产物 | 只影响存储选型（1.4） |
| P13 | 护栏 | 写入类动作一律经闸门 + 人工确认 | 与编排实现无关（4.8） |

**P1 需拆成三档判定，这是本轮修正的一处过度断言**：原表写"只有自研满足，框架均不满足"不成立 —— 准确说法是"配置可以驱动建图（都能）、零重启重编译（需自研）、attempt 语义（需自建业务层）"。三者叠加才推出自研，中间任何一档单独都不足以排除框架。

**P1 仍是主分水岭**（零重启 + attempt 两档只有自研同时满足），**P9 是第二分水岭**：重复提交与重做是业务概念，框架的 checkpoint 是运行概念，两者错位。

### 1.2 候选能力对比

**候选集必须包含非 AI 的工作流引擎。** P1、P4、P8、P9 四条都是工作流需求，只有拿工作流引擎一起比，"自研"才是被证明的选择而不是唯一可比对象（此为原表的一处候选集偏差，本轮补入）。此处只列能力形态，不做具体产品选型。

| 能力维度 | LangGraph | LangChain | Qwen-Agent | LlamaIndex | 通用工作流引擎 | 自研编排 |
|---|---|---|---|---|---|---|
| **① 配置驱动建图（P1）** | 可（数据构造图） | 可 | 可 | 可 | 可（流程定义即数据） | 可 |
| **② 零重启重编译 + 版本快照（P1）** | 需重启进程 | 需重启进程 | 需重启进程 | 需重启进程 | **原生支持**（定义改后新实例生效） | **支持**（compile() 是配置→计划编译器） |
| **③ 多次尝试的幂等语义（P9）** | 不内建 | 不内建 | 不内建 | 不内建 | 不内建 | **支持**（attempt 落在业务流转记录上） |
| 状态持久化 / 挂起恢复（P4） | 原生 | 需自建 | 不支持 | 需自建 | 原生（定时器 + 状态机） | 需自建，但模型简单（一条状态行 + 一组确认记录） |
| 领域状态集合约束（4.1） | 需自建 | 需自建 | 需自建 | 需自建 | **需自建**（通用状态机不认识业务允许状态集合） | **支持**（编译器校验） |
| 发布期阻断式校验（4.9） | 无 | 无 | 无 | 无 | 弱（流程校验 ≠ 配置发布校验） | **支持**（校验器） |
| 通用 Agent 能力 | 强 | 强 | 中 | 弱（偏检索） | 无 | 无 |
| 工具权限粒度 | 节点级可控 | 靠 prompt | 靠 prompt | — | 任务级可配 | 声明式配置，天然可审计 |
| 内网离线部署（P2） | 支持 | 支持 | 支持 | 支持 | 支持 | — |
| 依赖体积 / 升级风险（P7） | 中 | **高** | 低 | 中高 | **高**（JVM 栈、升级节奏不由自己定） | 无 |
| 学习与调试成本 | 中 | 高 | 低 | 中 | 中高 | 低 |
| 结论 | **限定场景采用** | 不采用 | 不采用 | 暂不采用 | **不采用**（P7 + ①③ 仍需自建，等于多背一层） | **业务编排采用** |

**P7 是双刃的，本轮明确记账。** 自研是本方案长期维护成本最高的一端（编译器 + 五态失败 + attempt 幂等 + 两级校验 + 三层 Context 装配）。所以 P7 同时被用来：

| P7 的两副面孔 | 处置 |
|---|---|
| 排除重依赖框架（LangChain、通用工作流引擎） | 1.5 框架延后装，机制落地期零 Agent 依赖 |
| 抑制自研规模 | 4.2 砍掉通用编排器（无任意 DAG、无表达式引擎、无并行汇聚），把表达力限定成「有序节点 + 绑定 + 执行资源 + 责任人」 |

**减法必须先做，加法才允许。** 「自研」不是"少依赖所以更轻"，而是"必须自己扛的表达力被主动缩小了"。若后续 4.2 的边界被放宽（加入任意分支 / 表达式引擎），P7 就不再支持自研，应重新比选。

### 1.3 关键判断：配置是数据，图不能是代码

这是全案的地基判断，来自 P1 的第 ② 档（零重启重编译）。

把运行期可变的配置编译成代码再部署：

```
把配置编译成代码再部署
  → 每次改流程 = 改代码 + 评审 + 发版 + 重启
  → 与 P1 第 ② 档直接冲突
```

配置数据与流程代码是两件事，不能互相转化（把数据编译成代码就丢掉了"运行期可变"这个性质）。注意区分：框架可以**用数据构造图**（① 档），缺的是"改完配置不重启就重编译"（② 档）。

所以分两层，各管一段：

| 层 | 承载 | 形态 | 变更频率 |
|---|---|---|---|
| **业务编排** | 域、节点序、数据绑定、执行资源绑定、责任人 | 配置数据 → 运行期编译成**可查询的执行计划** | 高 |
| **Agent 编排** | 多步推理：归因、起草、澄清 | 图（相对稳定，每次 3~8 步） | 低 |

关键区别：**业务编排的"图"是编译产物**（可查询、可快照、可比对），Agent 编排的"图"是代码。业务侧改流程不需要碰 Agent 侧一行代码。

### 1.4 选型清单

| 层 | 选型 | 依据 |
|---|---|---|
| 后端 | **FastAPI（Python）** | P6（存量脚本语言）、P7 |
| 业务编排 | **自研编译器 + 关系库事务状态机** | P1（②③ 档）、P4、P8、P9；规模受 P7 约束，见 1.2 末 |
| Agent 编排 | **LangGraph**（checkpointer 落库） | P4 的挂起恢复；P9 场景不落这里 |
| 确定性介入 | **纯规则函数，0 LLM** | P8、P10 |
| 调度 | **APScheduler + 持久化 JobStore** | 轻量、可嵌入、支持 misfire 策略（P7） |
| 推理服务 | **OpenAI 兼容端点**（vLLM 等） | P5、P10：可换、可独立降级 |
| 存储 | **PostgreSQL（含向量扩展）** | 业务数据与向量同库 |
| 产物存储 | **现有共享存储 + 元数据登记** | P12：不搬迁存量产物 |
| 部署 | **容器编排 + 按能力打标的 Worker 池** | P2、P6；推理节点与应用节点分开，故障域隔离（P10） |

### 1.5 一条实施原则：框架延后装

通用 Agent 框架是全案唯一「依赖重、收益窄」的组件。在还没确定哪些介入真的需要多步推理之前引入，等于先背依赖再找场景。

| 阶段 | 引入 | Agent 侧形态 |
|---|---|---|
| 机制落地期 | 后端、配置层、编排、执行、调度 | 全部规则化，**零 Agent 依赖** |
| 接入真实数据后 | 逐条评估介入场景，**先写规则版本** | 能用规则表达的一律规则化 |
| 确认某场景规则表达不了 | 该场景单独引入 LangGraph | 只接该场景，不改其余 |

判据：**规则能表达的介入不要用 LLM**。这既是 P8，也是算力预算的主杠杆（见 3.6）。

## 2. 工具注册与调度

### 2.1 工具是配置项，不是代码里的列表

关键取向：**工具的能力契约是数据，工具的实现可以是任何语言 / 任何进程**。这样执行资源才能独立演进，主系统不因工具语言而变。

与 P6 的关系要分清，避免读成矛盾：

| | 说法 |
|---|---|
| **P6（偏好）** | 存量执行资源是 Python，所以新工具**默认**同栈、Worker 默认同栈 —— 省掉跨语言的数据格式翻译 |
| **P6 不是** | 契约不绑定实现语言。新增工具可以是任意语言 / 任意进程，只要通过输出 schema 准入（2.2）即可 |
| **防格式不一致靠** | 统一输出 schema + 同类执行资源共用同一明细结构（2.2、3.8），**不是**同语言 |

所以"同语言"是省事的默认选择，"契约统一"才是正确性保证 —— 后者不可省。

注册中心是 SSOT，注册形态是**声明式**：

| 注册方式 | 优点 | 代价 | 取舍 |
|---|---|---|---|
| 声明式（表 / 声明文件） | 契约与实现分离；非开发可读可改；实现语言无关 | 需引擎读配置并做校验 | **采用** |
| 装饰器（框架内注册） | 少写配置 | 契约与框架耦合；非开发改不了；绑定实现语言 | 不采用 |

### 2.2 工具契约的字段分类

字段按"性质"分五类，与工具做什么无关。

| 类别 | 字段 | 作用 |
|---|---|---|
| **标识** | 唯一 key、名称、分类 | 主键；分类用于调度与统计 |
| **契约** | 输入 schema、输出 schema、**终态语义**、**契约版本 + 兼容区间** | 见下方说明；版本演进见 6.4 |
| **归属** | owner（必填）、文档、样例数据、回归用例集 | 故障时通知谁；改动后如何自动验证没改坏 |
| **执行策略** | 执行位置类型、超时、重试策略、幂等键模板、耗时档位 | 调度器据此排队、限流、失败重试 |
| **权限与状态** | 谁能手动运行 / 谁能被调度触发、是否需要人工确认、启用 / 封存 | 新增工具不改代码；封存走状态位而非删除 |

**「终态语义」是契约的一部分，不只是执行结果。** 契约必须声明本次执行可能落在哪个终态上，每种终态的输出体结构：

| 终态 | 输出体要求 |
|---|---|
| `success` | 完整输出 + 结构化明细 |
| `skipped` | `missing_dependency: [{dep_id, why, blocked_entity_ref}]` + 空明细。**跳过是合法输出，不是空输出** |
| `failed` | 明细 + 失败原因分类 |
| `error` | 错误类别 + 可重试标记 + 错误栈 |

不声明这一条，`skipped` 的输出就没有结构，下游只能靠猜 —— 这是"跳过被当成成功"的根因。

#### 契约版本与兼容区间

**两条版本轴必须分开**，混为一谈会出四类事故：

| 轴 | 内容 | 升级方式 |
|---|---|---|
| **执行资源版本** | 实现变了（性能、bug 修复、内部重构） | **透明升级**，契约不变，配置零改动 |
| **契约版本** | 接口变了（字段增删改、必填性变、**语义变**） | 需兼容判定，发布期拦截 |

配套四条规则：

1. **配置里存契约版本号，不存契约形状。** 契约注册中心**永久保留全部历史版本**（不可删除 —— 老配置要永远能用，不像代码可以删）。
2. **兼容区间由契约声明**，编译期（4.6）检查每个绑定是否落在区间内；不在区间内 → 发布期阻断（4.9）。
3. **语义变更必须升版本号，即使 schema 形状完全没变。** 形状比对只能当辅助，版本号由人显式管理。
4. **产物写入时记 `produced_by: { tool, contract_version }`** —— 历史数据永远可解释。这是全案唯一「现在不做，以后补不回来」的动作（6.4）。

**执行资源版本不进幂等键**（2.5）—— 否则工具一升级全部重跑。但要记进运行记录。

三条准入硬规则：

1. **输出 schema 不统一不予注册** —— 下游消费（含 Agent）依赖统一契约。
2. **owner 不可为空** —— 没有归属的工具，故障时无人可通知。
3. **样例与回归用例齐备** —— 无回归的工具，改动后无法判断有没有改坏。

### 2.3 执行资源按能力分层

按**执行时的能力需求**分，不按工具用途分。

| 层 | 判据 | 承载 | 新增工具要做的事 |
|---|---|---|---|
| **纯计算** | 无本地状态依赖、无图形界面、不接外设 | 通用 Worker 池（可横向扩） | 写实现 + 填契约 |
| **需特定环境** | 依赖 OS 特性、原生组件、外设、特定客户端 | 专用 Worker 池，**按能力标签匹配** | 同上 + 声明能力标签 |
| **需外部授权或人工** | 目标系统无接口，或写操作需人工授权 | **不派发执行**，只产出数据包 + 待办 | 填契约时声明需确认 |

第三层是正式的执行位置类型，不是降级兜底。语义是：**系统负责把"要做什么"整理成人可执行的产物并登记待办；执行动作本身保留在授权方手里**（对应 P3、P11、P13）。

这一层是 **P11 的直接推论，不是可选的兜底设计**：上游系统无写接口（P11）叠加签字 / 授权动作不可代行（P13），"系统代为执行"在责任上根本不成立，因此这一层是一期就要建的正式能力。

### 2.4 绑定与派发

**绑定是配置的一部分**：每个节点声明「完成时触发哪些执行资源、产出哪些交接物」。改绑定改配置，不改代码。

| 项 | 规则 | 理由 |
|---|---|---|
| **触发时机** | 节点提交时触发，不等待执行完成 | 用户不该等长任务跑完；提交必须快速返回 |
| **事务切分** | 事务 A（同步，毫秒级）：推进状态 + 写派发记录；事务 B（异步）：执行 | 状态是事实必须先落；执行失败不能回滚已提交的录入 |
| **执行失败** | 不回滚业务状态，转告警 + 事项，产物最终一致 | 业务流转不能被工具失败拖停 |
| **未声明执行资源** | 不自动派发，走线下；同时运行期校验告警 | 系统不做"聪明"的自动补派 |

### 2.5 幂等与「尝试号」

派发幂等键：

```
sha256( domain_id + entity_id + node_id + plan_version + attempt + tool_key + input_fingerprint )
```

`attempt` 是这套机制里最容易被实现错的一个字段，规则如下：

| 规则 | 说明 |
|---|---|
| **attempt 是业务概念，不是运行概念** | 由业务事件推进（回退确认、修正完成），**不由派发器自增** |
| 正常首提 | attempt = 0 |
| 回退重做 / 修正后重做 | attempt + 1 |
| attempt 落在实体-节点的流转记录上 | 不落在派发表里，否则派发重试会被误判成新尝试 |

`attempt` 必须在幂等键里的原因：**没有它，回退重做会被幂等吞掉** —— 回退后重新提交时，若输入未变，键与首提相同 → 命中上次成功记录 → 不重跑，而业务上重做就是要重跑产出。加上 attempt 后：同 attempt 内重复提交不重跑（幂等），跨 attempt 必重跑（重做语义），两者同时正确。

同理 `plan_version` 进键：配置改版后同一节点语义可能已变，不该复用旧结果（域级版本机制见 4.6）。

### 2.6 调度：两类触发源

| 触发源 | 机制 | 适用 |
|---|---|---|
| **事件驱动** | 业务事件 → 派发 | 提交、回退、修正、登记完成、配置发布 |
| **时间驱动** | 时间规则到点触发 | 周期批处理、回归批量 |

**优先级按"谁在等"排，不按"谁触发"排。** 原设计把不在同一层的机制放进同一张表，会导致不可执行的排序：

| 档 | 谁在等 | 内容 | 队列 |
|---|---|---|---|
| **P0** | 前台用户在等 | 节点提交派发；人工点「运行」且选了同步等待 | 通用 Worker 独立槽位，至少 2 |
| **P1** | 无人等，但会卡住别人 | 登记完成 → 唤醒下游所需的派发；依赖下游开工的前置派发 | 快速通道 |
| **P2** | 无人等 | 周期批任务、批量回归 | 低峰批量 |
| **不进队列** | —— | **提醒 / 跟催 / 巡检 / 卡点判定** | 规则内核内同步判断，毫秒级、0 token |

最后一行是关键修正：**提醒与跟催不是任务**，它们是规则函数，不占 Worker 槽位、不进调度队列。把它们列进工具优先级表是分类错误。

**关于并发规模**：P0 的定义是"前台用户在等"，一个用户最多同时等一个派发，因此 **P0 并发数 ≈ 同时在提交的人数**。这个量从运行日志（每条记录含 user + 时间戳）直接可算，**不需要专门压测或等实测报告**。真正需要实测的只有推理侧并发档位，而推理按 1.5 延后上线（6.5）。

调度器四条策略：

| 策略 | 决策 | 理由 |
|---|---|---|
| **misfire** | 错过的周期任务**不补跑**，标记 missed 并补告警 | 补跑把过期输入与新数据混合，产出错误结果。正确动作是让人知道没跑 |
| **任务级超时** | 覆盖工具默认超时 | 无超时的任务会占死 Worker 槽位，拖垮 P0 |
| **周期任务幂等** | 同一「任务 + 业务周期」只成功执行一次 | 调度重试或多实例抢锁时不产生重复产物 |
| **积压监控** | 队列深度超阈值即告警，不等任务超时 | 堵了要立刻知道 |

### 2.7 失败分级（五态）

四态不够用（看板把"跳过"算成"成功"是数据失真），但把推理不可用混进执行失败同样是数据失真。正确划分是**五态 + 推理单独一类**：

| 状态 | 判据 | 语义 | 是否重试 |
|---|---|---|---|
| `success` | 执行完成且结果符合契约 | 成功 | — |
| `skipped` | 前置数据缺失，**主动未执行** | **未执行**（不得计入成功） | 否 |
| `failed` | 执行完成但结果不符契约 | 失败 | 否（重试无用） |
| `error` | 未完成（超时 / IO / 崩溃） | 异常 | 是（指数退避 ≤N 次，仅限可重试类别且任务幂等） |
| `inference_unavailable` | 推理排队超时、模型不可达、限流拒绝 | **推理未发生**（不是执行失败） | **否**（重试推理纯浪费算力） |

`inference_unavailable` 单列的理由：混进 `error` 会触发重试，浪费算力，并污染业务失败率指标。正确处置是**降级为「留待人工」+ 告警，不影响业务流转**（详见 3.9）。

配套：每条非 success 记录必须能回答「**影响了什么**」—— 缺前置数据记 `missing_dependency`（2.2 的契约字段），这是把"跳过"变成可处置信息的关键。

告警三路并行：审计日志（必写）+ 控制台 + 推送给 owner。

### 2.8 人工确认是契约字段，不是代码分支

确认点写在工具契约里（`confirmation: required | none` + 确认角色集合），不写在流程逻辑里。

| 收益 | 说明 |
|---|---|
| 新增需确认的工具不改代码 | 改配置即可 |
| 确认位置随工具走 | 工具在哪个节点被派发，确认就在那个节点前 |
| 可审计 | 契约声明了"需确认"，运行时缺确认即违规，能检出 |

确认后的执行时机有一条硬规则：**恢复执行前重拉一次最新事实**（见 3.7）。

## 3. Context 管理机制

### 3.1 为什么不用框架自带的记忆

框架的会话记忆（摘要 / 向量记忆 / 消息历史）解决的是"模型记不住上一轮"。本系统的问题不是记不住，而是**记错了更危险**：

- 业务状态随时在变（别的环节在提交、回退、修正）。
- 把状态内容拷进提示词或检查点，会产生与库不一致的副本；模型据副本判断，结果是错的且无法追溯。

原则：**事实不入提示词，只入指针。** 模型通过工具自己取，取到的永远是库里的当前值。

### 3.2 三层 Context

| 层 | 内容 | 生命周期 | 预算 |
|---|---|---|---|
| **L0 系统层** | 主体身份与权限、介入边界白名单、可用执行资源清单、生效配置版本指针 | 常驻，可前缀缓存 | 小且稳定 |
| **L1 任务层** | 当前实体主记录、明细摘要、所在节点及其配置、相关告警与未闭环事项、系统事件时间窗 | 每次任务组装 | 中 |
| **L2 检索层** | 非结构化文档片段；结构化产物的明细摘要 | 按需 | 受裁剪 |

L0 走前缀缓存（命中率高），实际成本远低于面值 —— 这也是 3.6 里 L0 预算看起来不小却不贵的理由。

### 3.3 实体锚定

**一个任务只围绕一个实体**（业务实体 id / 单据号 / 事项 id）。

无单一实体的聚合型请求（"今天跑了什么"、"当前有哪些待办"）**降级为规则聚合**：查询层直接产出结构化清单，不进 LLM；模型最多做转述。

理由：多实体场景塞给模型，上下文体积失控且结论不可靠；而这类查询本来就用结构化查询能答得更准。

### 3.4 引用式加载与裁剪

**引用式加载**：提示词里放元数据（名称、位置、条数、生成时间、状态），模型判断需要细节时自己调工具取。主上下文始终很小，细节按需且始终新鲜。

**裁剪预算**：超预算时按固定优先序裁。

| 裁剪序 | 内容 | 裁法 |
|---|---|---|
| 1 | 明细流水 | 保留最近 N 条 + 汇总；超出则中间折叠 |
| 2 | 产物明细行 | 只入 top-K + 总数 + 分布统计 |
| 3 | 低优先级告警 | 只入计数，不入明细 |
| 4 | 系统事件 | 时间窗从大收到小 |
| 5 | 检索片段 | top-K 降低 |

**裁剪必须透明化**：把"裁掉了什么、按什么规则裁的"写进上下文元信息。模型必须知道自己的结论有边界，而不是假装看全了 —— 这是防止过度自信结论的主要手段。

### 3.5 按数据形态的准入表

与具体表名无关，按形态判定。

| 数据形态 | 入 Context | 理由 |
|---|---|---|
| 结构化业务记录（实体主记录） | 入 | 精确、可查、体量可控 |
| 结构化明细 / 流水 | 摘要后入 | 全量必然超预算 |
| 结构化产物明细（对账 / 比对结果） | **按条数裁剪后入** | 明细可达上千条，裁剪见 3.4；结构本身由工具契约保证（3.8），装配层不做二次转换 |
| **离线补录数据** | 入，但**必须带标记** | 质量低于在线数据；Agent 归因引用它时要能识别（6.6） |
| 非结构化文档 / 规范 | 检索后入 | 全文过长，top-K 片段足够 |
| 二进制产物（图像、压缩包） | **仅元数据** | 模型不能可靠判读，且体积失控 |
| 配置文件与源代码 | **不入** | 模型读代码诊断易发散；应看结构化运行日志与错误栈 |
| 权限 / 配置全表 | 裁剪后入 | 只入当前主体可见范围 |
| **草稿态配置** | **不入** | 未生效配置不能作为判断依据，会用未来的规则评现状 |

### 3.6 预算与算力对齐（P5：成本）

单次上下文预算：

| 层 | 目标 |
|---|---|
| L0 | 小且稳定，靠缓存摊薄 |
| L1 | 主体：实体主记录 + 节点配置 + 未闭环事项 + 时间窗事件 |
| L2 | 受裁剪的检索片段与产物明细摘要 |
| 输出 | 短（结论 + 依据 + 建议，不复述上下文） |

**本地推理（P2）有两笔成本，只算 token 会低估一个量级。** P5 是"预算封顶 + 本地"，P2 又禁止用外部 API，于是常驻算力变成固定支出：

```
月成本 = 常驻算力（不随调用次数变化）+ 变动 token 成本

常驻算力 = 本地推理实例数 × 单实例月折旧     ← 与「需推理占比」无关，占用即付费
变动 token = Σ(每次调用)
             ├ 输入 token 未命中缓存 × 输入单价
             ├ 输入 token 命中缓存   × 输入单价 × 缓存折扣
             └ 输出 token            × 输出单价     ← 输出通常显著贵于输入

日调用次数 = 业务事件总数 × 需推理占比        ← 其余全部规则化，不计费
```

两条由此推出的判断（原公式漏掉）：

| 判断 | 说明 |
|---|---|
| **常驻算力是阶梯式的** | 峰值并发决定需要几台实例。低于阈值时多备一台的代价很高，所以"并发档位"（6.5）最终是要花钱的决策，不只是性能参数 |
| **推理延后上线（1.5）同时省下常驻算力** | 机制落地期需推理占比 = 0，常驻算力也可为零。这是 1.5 之外的第二条经济理由 |

三条杠杆，按收益排序：

1. **降低「需推理占比」**（把介入规则化）—— 主杠杆，降的是**调用次数**，收益一个量级，且直接决定常驻实例数该配几台。
2. **提高 L0 缓存命中率** —— 次杠杆，L0 是常驻内容，命中率应 >90%。
3. **压单次 L1 预算** —— 第三杠杆，且**不能压 L1 主体**（压了损质量，得不偿失）。

一条纪律：**不要靠压提示词省钱，要靠少调用。** 压提示词降的是质量，换来的是 token 账单，方向错了。

结论：算力预算能否达成，取决于**介入场景里需要多步推理的占多少**，不取决于选哪个框架。所以先做规则版介入、再决定是否引入 LLM，顺序不能反。

### 3.7 指针化持久状态 + 确认前重拉

```
推理会话     = 无跨轮记忆
持久化检查点 = { 会话 id, 已走步骤, 待确认动作, 已用工具的引用 }
事实         = 每次回查库与存储
```

推论：

- 检查点**存"查过什么"的指针，不存"查到了什么"的内容**。恢复时按指针重取，保证新鲜。
- 澄清式追问（"你指 A 还是 B？"）靠会话内已用工具的结果，不靠模型回忆。
- **人工确认挂起后，恢复执行前强制重拉事实。** 挂起可能持续数小时，期间状态可能已被别的环节修正、配置可能已改版、产物可能已重新生成。用挂起时的旧事实执行，会产生无法追溯的不一致。

这里消除的是**触发场景**（把"读事实"和"写动作"在时间上强制拆开，中间不留可复用的旧值），不是在校验环节加兜底。

#### 这条机制付出的代价：推理结论事后不可复现

必须把取舍写明，否则 P8「可复算」会被误读成全系统可复算：

| | 编排与校验 | 推理结论 |
|---|---|---|
| 可复算 / 可复现 | **是** —— 配置 + 状态 + 留痕三者齐备，可重放、可比对（P8 硬要求） | **否** —— 本方案显式放弃 |
| 原因 | 状态与事件都持久化 | 检查点只存指针不存事实 + 恢复前强制重拉 ⇒ 挂起期间事实可能已变，当时的输入值没有落盘 |
| 替代手段 | —— | Agent 审计线记录**数据源清单 + 依据**（4.10 第三条线）：能回答"这个结论当时依据了哪些数据"，但**不能**回答"当时这些数据具体是多少" |

所以「事实不入提示词、不入检查点」是一条**用可复现性换新鲜度与正确性**的取舍：新鲜度优先（P8 的另一半 —— 编排确定性），代价由审计清单部分补偿。真正的补救只有一条：**结论若要长期作为依据，必须落成结构化记录并写明 src**，不能只留在会话里。

### 3.8 工具输出要「可被消费」

结构化明细**由工具契约保证**，不是 Context 装配层的职责。契约里对明细类输出的硬要求：每条至少含

| 要素 | 作用 |
|---|---|
| 实体标识 | 能关联回业务状态，否则无法落回流程 |
| 字段名 | 差异在哪个维度 |
| 两侧取值 | 依据 |
| 严重度分档 | 与告警级别**共用一套分档**，才能「明细 → 告警 → 事项」三级按级别联动 |
| 来源标识 | 哪个执行资源产出，否则同类资源口径冲突会让归因拿到互相矛盾的证据 |

配套要求：**同类执行资源必须共用同一明细结构**。口径不统一的比对资源，比没有更糟。

Context 装配层只做裁剪（3.4）与准入过滤（3.5），不做二次格式转换。

### 3.9 推理不可用时的降级（P10）

推理服务不可用时，系统的行为必须是确定的：

| 场景 | 行为 |
|---|---|
| 模型不可达 / 限流拒绝 | 记 `inference_unavailable`，不重试 |
| 排队超时 | 同上，并记录排队时长 |
| 上述任一 | 降级为「留待人工」：事项仍在，责任人仍在，只是没有模型起草 |
| 中枢与业务流转 | **完全不受影响** |

最后一行是 P10 的兑现，也是把 Agent 限定在只读 / 起草的真正价值：**推理是增强项，不是关键路径**。

判断标准：把推理服务整个停掉，系统应当只是"起草能力消失"，而不是"流程停摆"。如果做不到这一点，说明有本该规则化的逻辑被塞进了模型（回看 1.5 的判据）。

### 3.10 反模式

| 反模式 | 为什么禁止 |
|---|---|
| 把业务数据全量塞进上下文 | 演示环境数据量小可以，真实规模必然超预算；必须在查询层过滤 + 限条 |
| 把文件内容读成文本进上下文 | 体积失控；且模型对大表数值比对不可靠 |
| 用向量检索查结构化状态 | 结构化数据走查询，检索只用于非结构化语料 |
| 让模型决定责任人 / 归属 | 归属是配置解析（优先级链，4.7），确定性可复算（P8）；模型只描述结论 |
| 把草稿态配置喂给模型 | 同 3.5 |
| 用"谁在什么时候点过运行"当根因证据 | 根因要看状态流转 + 交接物就绪情况 + 明细，不是看操作流水 |
| 多实体问题直接问模型 | 降级为规则聚合（3.3） |
| 为省 token 压缩提示词 | 方向错（3.6），降质量换账单 |
| 把"记忆"当能力补 | 事实回查，记忆只会引入过期副本（3.1） |

## 4. 中枢的编排

### 4.1 配置模型顶层：域与实体归属

配置与执行计划都是**按域独立**的，域是顶层容器：

```
域 (Domain)                        ← 一个完整业务闭环
  ├ 属性：id / 名称 / 状态(active|stopped) / 允许状态集合 / 节点列表 / 生效版本
  └ 节点 (Node)：有序列表
       ├ 属性：角色、默认责任人、时限(默认值)、字段与校验、执行方式、是否允许跳过
       └ 绑定：输入交接物、输出交接物、执行资源
```

四条规则：

| 规则 | 内容 | 理由 |
|---|---|---|
| **执行计划按域编译** | 每个域独立编译出自己的执行计划与快照，**不是一张全局图** | 改一个域不影响其他域；快照与漂移基线都按域独立成立 |
| **实体创建时绑定域 + 版本** | 实体记录 `domain_id` + `plan_version` | 域归属是实体的固有属性，后续一切派生都从这里开始 |
| **域可停用，不需要域迁移** | 域状态 `active / stopped`；stopped 后停止新建实体，域内在途实体按各自锁版配置跑完再归档 | 域结构变动（拆分 / 合并）不需要动已有实体，与 4.6 锁版同一哲学 |
| **跨流转用「终止 + 新建」** | 实体提前转出另一条流程 = 原实体置 `terminated`（记原因）+ 在目标域新建实体并带 `ref_to` | 两域留痕各自完整不被污染；转移原因一查 `ref_to` 就知；不需要状态兼容性判定 |

**明确不做域迁移**（论证见 6.3）。需求里的"迁移"几乎总是两种情况，处理方式都更简单：

| 真实场景 | 处理 | 为什么不需要迁移 |
|---|---|---|
| 域被拆分 / 合并 | 旧域置 stopped，在途实体跑完归档，新实体进新域 | 已有实体按旧配置跑完才是正确的；迁移会同时破坏锁版与状态语义 |
| 实物流转中要跳到另一条流程 | 终止 + 关联新建 | "迁移"最麻烦的部分就是状态兼容性判定，这条路完全绕开它 |

跨流转的落地要求：`terminated` 是终态（与 4.11 的终态冻结一致，不可退回、不可修正）；新实体的 `ref_to` 必须写审计，否则"这台机为什么提前转出"无从追溯。

### 4.2 划清「可配置」的边界

**可配置 ≠ 任意编排。** 配置的表达能力必须被限定，否则 P1 的自由度会连带废掉校验、派生、巡检、追溯。

**配置能表达**：

| 维度 | 表达力 |
|---|---|
| 域 | 新增 / 停用；状态集合定义 |
| 节点 | 有序列表，可增删改、换序、分组 |
| 节点属性 | 归属角色、默认责任人、时限、字段与校验、执行方式、是否允许跳过 |
| 数据流 | 每个节点的输入绑定 + 输出绑定（绑定到登记过的交接物） |
| 执行资源 | 节点挂哪些执行资源 |
| 交接物 | 登记中心：格式、传递方式、落点 |

**配置不能表达**：

| 不做 | 理由 |
|---|---|
| 任意有向图 / 任意分支与并行汇聚 | 见下方对照 |
| 运行时逻辑表达式 | 要逻辑 → 要么注册成执行资源，要么改配置；不提供表达式引擎 |
| 绕过确认点的写操作 | 契约与代码双重约束 |

**为什么必须有边界**：

| 若无边界（通用编排器） | 若有边界（有限表达） |
|---|---|
| 链路是否可解析**无法静态判断** | 边由输入输出绑定推导，**可静态校验** |
| 下一环节是谁**无法确定** → 待办派生做不了 | 顺序来自有序列表，**待办可从配置纯查询派生** |
| 没有可比对的基线 → **漂移巡检做不了** | 发布即快照，版本可比 |
| 执行路径不确定 → **责任可追溯做不了** | 执行路径由配置唯一确定 |
| 每次改流程都要懂编排语义 | 改配置是业务操作，不需要理解引擎 |

结论：**把表达力限定在「有序节点 + 绑定 + 执行资源 + 责任人」，换来校验、派生、巡检、追溯四项能力。** 通用编排器给的是自由，代价是这四项全部失效。

### 4.3 三层编排

```
编译期   配置变更时跑，跑的是编译器
         配置(草稿/已下发) → 发布 → compile() → 执行计划 + 快照
         频率：低

运行期   每次流转都跑，确定性，无 LLM
         事件 → 归属派生 → 派发路由 → 校验 → 留痕
         频率：高

Agent 期 规则命中后按需介入（唯一进 LLM 的一层）
         上下文装配 → 推理网关 → 模型 → 起草事项
         频率：中（可低峰批量）
```

单向依赖：编译期产出执行计划 → 运行期读计划执行 → Agent 期只读运行期数据。**Agent 期不回写执行计划，不改运行期状态。**

**P10 的兑现**：只有 Agent 期依赖推理服务。推理不可用时，前两层完全正常（3.9）。

### 4.4 组件与职责

第 3 节与第 4 节的接口就在最后两行：**上下文装配器**与**推理网关**。没有它们，Context 机制与中枢是脱节的两套设计。

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **配置层** | 域与节点配置的唯一真源，版本化，草稿 / 已下发两态 | 草稿不进业务派生视图 |
| **编译器** | 配置 → 执行计划（按域） | 产物是可查询数据，不是代码 |
| **事件总线** | 业务事件统一入口，幂等去重 | 事件是唯一触发源，不允许绕过 |
| **归属派生器** | 按优先级链解析有效责任人；产出待办四桶 | 结果缓存到节点上，不在渲染时重算 |
| **派发路由器** | 按节点声明路由到四种去向 | 未声明的不自动派发 |
| **并发闸** | 实体乐观锁 + 派发唯一约束 | 见 4.11 |
| **校验器** | 发布期阻断 / 运行期告警，两级 | 见 4.9 |
| **留痕器** | 三条留痕线 | 见 4.10 |
| **闸门** | 人工确认挂起 / 恢复 | 恢复前重拉事实 |
| **上下文装配器** | 实体锚定 → 三层 Context → 准入过滤 → 裁剪 → 提示词 + 裁剪元信息 | 事实不入提示词（3.1）；裁剪必须透明（3.4） |
| **推理网关** | 统一推理入口：限流、排队、降级、审计 | 不可用时降级「留待人工」（3.9），不进业务失败统计 |

#### 事件分类：中枢的唯一触发源

所有编排动作都由事件触发，不允许绕过事件总线直接调用组件。

| 类别 | 事件 | 中枢动作 |
|---|---|---|
| 业务流转 | 节点提交、确认提交、**实体终止 / 跨流转转出** | 事务 A 推进状态 + 记录待派发 → 事务 B 派发 → 唤醒下游 → 留痕；终止时置终态 + 建关联实体 |
| 业务回撤 | 回退发起 / 确认 / 拒收 | 回拨到目标环节 → 重做后**快速归位**发起环节（不重走中间节点）→ **attempt + 1**（2.5）→ 校验归位一致性 |
| 业务修正 | 字段修正、数据修复 | 历史不覆盖（原值保留 + 新值 + 理由）→ 下游产物自动标**待重核**；数据修复走同一事件类别（6.2） |
| 数据到位 | 人工交接物登记完成、**离线补录提交** | 置就绪 → 检查下游输入是否齐 → 齐则唤醒；离线补录额外记标记与双时间戳（6.6） |
| 配置变更 | 配置发布 / 停用 / 下线 / **版本回退** | 编译期校验（含契约兼容性，4.9）→ 写快照 → 重建漂移基线 → 留痕 |
| 调度 | 时间规则到点 | 按任务类型路由（批处理 / 待人工确认 / 纯规则提醒） |
| 执行反馈 | 成功 / 跳过 / 失败 / 异常 / **推理不可用** | 分级处置（2.7）→ 告警 owner → 生成事项草稿 |
| 外部输入 | 上游系统事件、状态变更 | 只读入库 → 卡点判定（确定性规则） |
| 人工动作 | 确认完成 | **重拉最新事实** → 执行 → 置就绪 |

三条不变量：

1. **状态变更与流转事件必须同事务**（4.10）—— 否则出现"状态变了但没记录"的漏洞。
2. **配置类事件必须过发布期校验**（4.9）—— 不合规配置不产生快照，也不产生新版本。
3. **人工动作事件必须触发重拉**（3.7）—— 不复用挂起时的旧事实。

### 4.5 Agent 介入的完整链路

这张图把四节缝在一起 —— 前三节是各自机制，这一节是它们串起来跑的路径：

```
① 运行期规则命中（确定性，无 LLM）
        ↓
② 上下文装配器
   实体锚定 → L0/L1/L2 组装 → 准入过滤 → 裁剪 → 提示词 + 裁剪元信息
        ↓
③ 推理网关
   限流 / 排队  ── 不可用 ──→ 记 inference_unavailable，降级「留待人工」，流程继续
        ↓ 可用
④ 模型输出 → 结构化契约校验（不合规则丢弃，不进后续）
        ↓
⑤ 起草事项（不写业务数据）
        ↓
⑥ 需写操作 → 人工确认（闸门挂起）
        ↓
⑦ 执行前重拉事实（3.7）
        ↓
⑧ 写留痕（含 src 数据源清单，4.10）
```

**② 到 ⑧ 全部可替换**：②的装配规则、④的模型、⑥的确认角色都可换。唯一不可省的是 ①（确定性判定）、⑦（重拉）、⑧（留痕）。

### 4.6 配置编译：定义 → 执行计划 + 实体锁版

```
配置（草稿 / 已下发）
      │ 发布（校验器阻断不合规配置，4.9）
      ▼
compile()                          ← 运行期发生，数据驱动
      ▼
执行计划 EXEC_PLAN（按域）
  node = { id, 流转序位, 排配序位, 输入绑定, 输出绑定,
           执行资源, 默认责任人, 允许跳过, 状态 }
  edge = 由 输出绑定 ∩ 下游输入绑定 推导（不手绘）
      ├─→ 待办派生（纯查询）
      ├─→ 链路校验（静态可做）
      └─→ 快照（不可变，供实体锁版引用）
```

#### 实体锁版：在途实体用哪一版

**明确选择：实体创建时锁版，改版对在途实体零影响。**

| 规则 | 内容 |
|---|---|
| 锁版时机 | 实体创建时写入 `domain_id` + `plan_version`（= 当时该域的生效版本） |
| 读取规则 | 待办派生、时限、责任人、允许状态、执行资源绑定，**一律按实体的 `plan_version` 读，不读"当前最新版"** |
| 改版行为 | 域配置发布产生新版本；**已存在实体的 `plan_version` 不变**，新实体用新版 |
| **无例外通道** | 不提供"把在途实体切到新版"的配置能力 —— 一旦允许，锁版最核心的确定性就没了：改版瞬间会出现"部分已切、部分没切"的中间态，而这正是锁版要消除的东西 |

选这个的理由：

- 改配置瞬间，待办、时限、责任人全部**不会出现"一半实体用新版、一半用旧版"的中间态**。
- 不需要"在途实体迁移到新版"的逻辑，也不需要在途实体处理特殊分支 —— 这是最省事且最可解释的选择。
- 代价要认：新版配置对已存在实体不生效。业务上改配置通常是为了影响后续批次，这个代价值得。
- **"某个改动必须作用于在途实体"怎么办**（6.2）：三类动机各有更便宜的解法，真实剩下的那一点是**数据修复**，走业务修正事件（4.4 事件分类）—— 它本质是改数据，不是改配置。
- **时限是两层结构**：节点配置里存的是**默认值**（进版本），实际生效值允许**运行时覆盖层**（不进版本）。这样"临时延长提醒"不需要碰配置版本，重绑定需求从源头消失。

#### 快照的两个作用

| 作用 | 说明 |
|---|---|
| **实体锁版的载体** | 实体引用 `plan_version`，快照是该版本的不可变内容。要查"这个实体当时按什么配置跑"，查快照即可 |
| **漂移巡检基线** | 见下 |

#### 版本回退：锁版带来的免费能力

发布错了要能退。回退在锁版模型下极简单：

```
当前生效版本指针 ──指向──▶ v3
     └─ 回退 ──指向──▶ v2
```

**已有实体完全不受影响**（它们锁的是各自那版），只有回退后新建的实体用旧版。零数据迁移、零状态修正。

这是实体锁版的直接收益，也是"不做重绑定通道"（6.2）的另一面理由：不开放"改在途实体版本"，回退才可以简化成"移动一个指针"。

回退也是**审批的替代品**（6.1）—— 审批流解决的是"人会犯错"，回退解决的是"错了能退"，后者成本低一个量级。

漂移巡检因此从"版本不一致就提示"升级为**三档**（按域独立判定）：

| 情况 | 含义 | 动作 |
|---|---|---|
| 旧版无在途实体使用 | 纯版本推进，健康 | 无需动作 |
| 有在途实体在旧版，且旧版 ≠ 当前生效版 | 版本差 | 提示管理员，评估是否需要重绑定（6.2：无重绑定通道，此处只做提示） |
| 草稿长期滞留未发布 | 草稿不进业务，无功能风险 | 提醒；草稿态不参与巡检基线 |

最后一行修正了原设计的一个错误：草稿态配置本来就不参与业务，把它算进"漂移"会产生大量无意义告警。

### 4.7 归属派生：优先级链

```
节点默认责任人
  → 若该主体在此节点范围内有有效委托 → 代理人
  → 若无有效责任人 → 岗位队列（岗位兜底）
  → 全空 → 管理员兜底 + 校验器告警（配置缺陷，不静默）
```

待办分四桶：

| 桶 | 内容 |
|---|---|
| 我的待办 | 有效责任人 == 当前主体 |
| 同岗队列 | 无有效责任人，落到当前主体所属岗位 |
| 告警桶 | 未闭环告警指向当前主体 |
| 待确认桶 | 当前主体是某个待确认流程的目标方 |

两个工程要点（**不是优化项，是归属解析正确的必要条件**）：

1. **委托要按节点范围收窄**，不能只按岗位整体生效 —— 否则一个人委托了整个岗位，会把他并不负责的节点也一并带走，待办立刻错乱。
2. **委托登记要校验区间并参与判定** —— 无效区间不参与解析，登记时校验，避免登记了却不生效（或错误生效）。

### 4.8 派发路由：四种去向

| 去向 | 条件 | 动作 | 是否写业务数据 |
|---|---|---|---|
| **自动执行** | 节点声明了自动执行资源 | 入队 → 执行 → 写产物 → 置就绪 | 否（只写本系统表） |
| **人工登记** | 交接物声明为人工传递 | 生成待办 + 登记位；登记完成置就绪 | 否 |
| **Agent 起草** | 规则命中需起草 / 核对事项 | 入推理队列 → 出草稿 | 否（只出事项） |
| **闸门后执行** | 执行资源声明需确认，或写外部系统 | 挂起 → 人工确认 → 重拉 → 执行 | **是，且仅在闸门之后** |

两条硬规则：

- 未声明执行资源的节点**不自动派发**，走线下流程，同时运行期校验告警。
- 前三种去向一律不写业务数据。写操作只有一个入口：闸门之后。

这条规则的真实依据是 **P13（签字 / 授权类动作不可由模型代行）**，不是"技术上不信任模型"。P13 与 2.3 第三层（P11）叠加后，"写操作只有一个入口"既是合规要求也是责任划分，落成配置后还顺带获得可审计性（2.8）。

### 4.9 校验：两级，处置方式不同

**「只告警不阻断」只适用于运行期。配置发布期必须阻断** —— 断链配置发出去，运行时才派发失败，代价已经产生。这一条要分两级写：

| 级别 | 时机 | 处置 | 覆盖的校验 |
|---|---|---|---|
| **发布期校验** | 域配置发布时 | **阻断发布**，不生成快照、不产生新版本 | 引用完整性（绑定指向未登记的交接物 / 执行资源）；状态集合合法性；产出闭合（结构性断链）；**契约兼容性**（绑定引用的契约版本落在兼容区间内，2.2） |
| **运行期校验** | 提交时 / 定时巡检 | **只告警不阻断** | 派发完整性；逐项核对派发结果；漂移巡检 |

理由分两段：

- **发布期阻断**：配置错的时候拦住，成本最低（还没影响现场）。
- **运行期不阻断**：现场流转不能因配置或执行问题停摆。运行期发现的问题走告警 + 事项，由人处理。

运行期「派发完整性」的实现要点：**必须逐项核对，不能只判"全有 / 全无"**。只判有无会产生假阴性 —— 一项成功三项漏跑被算作通过，缺口永久隐身。这是这类校验最容易出错的地方。

### 4.10 留痕：三线分离

| 线 | 内容 | 写入时机 | 关键约束 |
|---|---|---|---|
| **业务流转事件** | 生产的推进与变更 | 与状态变更**同事务** | 不同事务会出现"状态变了但没记录"的漏洞 |
| **外部系统事件** | 上游系统来源的事件 | 外部事件入库时 | 供跨系统对账 |
| **Agent 与管理动作** | 谁 / 何时 / 做什么 / 结果 / **依据的数据源清单** | 每笔动作 | 独立于业务线，不混进业务时间线 |
| **产物来源标记** | `produced_by: { tool, contract_version }` | 产物写入时 | 历史数据永远可解释；**唯一不可延后的一项**（6.4） |

第三条线必须记录**数据源清单**，否则"为什么得出这个结论"不可追溯 —— 这是模型介入可解释性的最低要求。数据源清单由上下文装配器提供（4.5 步骤 ②），装配层不裁剪 src。

#### 离线补录的留痕（6.6）

线下兜底补录的数据必须可识别，因为它**质量天然低于在线数据**（照纸单重录、时刻不可信）。不标记的话，所有基于它的统计与 Agent 归因都会带一个未声明的误差。

| 要求 | 内容 | 理由 |
|---|---|---|
| **同一提交入口** | 补录走正常提交路径，不开第二个入口 | 单一真源。录入门槛低不是问题（正常路径本来就不多打字） |
| **双时间戳** | `occurred_at`（事实发生）+ `recorded_at`（进系统） | **两者差异本身就是需要核对的地方**；只记其一等于丢失信息 |
| **离线标记** | `recorded_offline` + 纸单号 | 纸单**不是真源**，只是录入的来源凭证 —— 保留编号用于追溯，不为它建第二套数据 |
| **质量降权** | 离线数据在派生统计与 Agent 归因中显式标记 | 归因引用了离线数据却不知道，结论就有未声明的误差 |

状态冲突由提交前置校验（4.11）**自然拦住**，不需要专门的冲突处理逻辑 —— 这是提交级校验的附带收益。

### 4.11 并发控制

P9 意味着并发窗口必然存在，要三层防护：

| 层 | 机制 | 挡住什么 |
|---|---|---|
| **实体级** | 实体行**乐观锁**（version 字段，CAS 更新状态） | 两个环节同时提交同一实体 |
| **节点提交级** | 状态前置校验：只有「当前 status == 该节点的流转序位」才允许提交 | 乱序提交、重复提交 |
| **派发级** | 派发记录**幂等键唯一索引** + 「运行中」记录态 | 并发窗口内的重复派发 |

派发记录四态流转：

```
pending ──→ running ──→ success | skipped | failed | error
   └────────────→ superseded（被更高 attempt 的派发取代，作废旧记录）
```

**并发窗口的处理必须写清楚**，因为"命中成功记录则不重跑"覆盖不到它：第一个请求已建 `pending` 记录但未完成，第二个请求进来时唯一约束冲突 —— 此时第二个请求**读取已有记录并返回其状态**，不新建、不重跑。这是标准做法，但漏掉就会双跑。

`superseded` 态的用途：回退重做时 attempt + 1，旧 attempt 的 pending 记录标为 `superseded`，避免旧派发晚到时把新结果覆盖掉。

### 4.12 编排原则

| 原则 | 含义 |
|---|---|
| **1. 配置驱动，不写死** | 流程是数据。改配置不改代码、不发版（1.3 的兑现） |
| **2. 实体锁版** | 在途实体按创建时的配置版本执行，改版只影响新实体（4.6） |
| **3. 流转序与排配序分离** | 业务事实与人的偏好分别存，互不覆盖 |
| **4. 提交与执行分离** | 状态先落（毫秒级返回），执行异步；执行失败不回滚已提交的录入 |
| **5. 幂等含 attempt** | 重复提交不重跑，回退重做必重跑（2.5） |
| **6. 校验分两级** | 发布期阻断，运行期告警（4.9） |
| **7. 写入只有一个入口** | 闸门之后；其余全只读或只出草稿 |
| **8. 事实即最新** | 执行前重拉，不复用挂起时的旧值（3.7）。**代价是推理结论事后不可复现**，由 Agent 审计线的 src 清单部分补偿 |
| **9. 推理在关键路径之外** | 停掉推理服务，系统只是少起草能力，不停摆（3.9） |
| **10. 边界先于能力** | 表达力限定在 4.2 的六项内。放宽边界要先回答"这是否还在 P7 可承受的范围内"（1.2 末） |

### 4.13 编排边界（明确不做）

| 不做 | 理由 |
|---|---|
| 用户自由拖拽连线编排 | 4.2 的边界论证；自由度的代价是四项核心能力失效 |
| 流程级并行 / 汇聚 | 见下方收敛结论 |
| 通用表达式 / 规则引擎 | 要逻辑就注册成执行资源，不在配置里藏逻辑 |
| 通用插件市场 / 沙箱 | 执行资源需要 owner 与回归契约，沙箱机制与"必须声明归属与回归"冲突 |
| 模型自主决定写操作 | 责任边界，不是可配置项 |
| 任务自动补跑（misfire 补跑） | 补跑把过期输入与新数据混合；正确动作是补告警（2.6） |
| 多租户 / 跨组织 | 单组织内网系统，无对应需求（P2） |
| **改上游系统以取得写接口** | P11：外部系统按现状使用，不为其改造。代价是 2.3 第三层成为一期正式能力 |

**并行与条件分支的收敛结论**（这两条原列为待确认，现已自答）：

| 问题 | 结论 | 实现方式 |
|---|---|---|
| **条件分支** | **不需要配置表达** | 执行资源判定后写状态；下游按「输入是否就绪」决定推进或跳过。分支逻辑在工具里，配置只记结果 |
| **节点跳过** | 支持 | 节点可选配「允许跳过」；跳过时下游不阻塞，转为标记"该输入未产出"，并进入校验与告警视野 |
| **并行** | **不在流程级引入** | 并行由「一个节点挂多个执行资源并发执行」实现（2.4 的绑定天然支持），而不是流程级并行汇聚。流程保持单指针，"当前环节"永远唯一 |
| **人工会签 / 逐级审批** | 一期单点确认 | 会签 = 多个确认角色，闸门从单点扩为集合；引擎与契约（2.8）不用改，故二期扩展成本低 |

## 6. 待确认项的收敛结论

六个待确认项已逐项分析。结论：**六项中五项可自答，且全部不阻塞一期；真正必须在动手前定下的只有一件事。**

| # | 待确认项 | 收敛结论 | 阻塞一期？ |
|---|---|---|---|
| 1 | 配置发布是否需要审批流 | **不做审批流。** 发布权 = 域级 ACL；建版本回退替代审批 | 否 |
| 2 | 是否需要紧急重绑定通道 | **不做。** 时限拆成「默认值（版本化）+ 覆盖层（运行时）」；真要改数据走业务修正事件 | 否 |
| 3 | 域迁移是否允许 | **不做。** 换「域可停用」+「终止 + 关联新建」两个更简单的机制 | 否 |
| 4 | 契约 schema 版本演进 | **两条版本轴分离；配置存契约版本号；产物自带契约版本号** | **部分：产物版本号现在必须记** |
| 5 | 峰值并发实测值 | **拆成三个量**，Worker 池规模从运行日志直接算，无需实测 | 否（推理上线后才需要） |
| 6 | 离线兜底数据对齐 | **同一提交入口 + 双时间戳 + 质量降权**；状态冲突由提交校验自然拦住 | 否 |

### 6.1 发布审批流 —— 问题问错了一半

它其实是两个可分离的问题：**谁有发布权**（权限）、**要不要被审批**（流程）。

**权限可以直接答**：发布作用域是**一个域**，所以发布权天然 per-domain ——「域归属负责人 + 管理员」一条 ACL 解决，不需要流程。

**要不要审批：不要。** 三条论证：

1. **审批流解决的是语义错误**（"这个节点不该由这个岗位负责"），但结构错误已被发布期校验拦住（4.9）。语义错误靠审批也拦不住 —— 审批人只是再点一次"同意"。
2. **审批流的真实代价是侵蚀 P1**：多一个人卡发布 → 配置与业务现实脱节 →"改配置不发版"这个核心价值被抵消。为拦低频错误赔上高频灵活性，不划算。
3. **审批会把配置态从两态变三态**（草稿 / 待审 / 已发布），连带 3.5 准入规则、4.6 漂移巡检都要多处理一个状态 —— 而待审态与草稿态在业务上都是"不进业务"，合并没有收益。

**该建的不是审批，是回退**（4.6）—— 锁版让它几乎免费。

> **触发重评的信号**：出现**两个以上角色**需要发布同一域的配置，且实际发生过误发布。届时再上审批。

**补一条：本节"不做审批"的真正依据是 P13，不是"一人开发"（P7）。** 签字 / 裁决类动作需要的是**执行时的双点确认**，而配置发布需要的是**发布前的责任确认** —— 两者不是同一个控制点。把发布审批当成对签字动作的兜底，会造出一个职责错位、且把人挡在错误位置上的流程。

### 6.2 紧急重绑定 —— 需求大部分是假的

四个动机里三个有更便宜的解法：

| 动机 | 真需要重绑定？ | 更好的解法 |
|---|---|---|
| 责任人变了（离职、调岗） | 不需要 | 责任人本就是运行时按优先级链解析（4.7），委托变更自然生效 |
| 时限要改（延长 / 收紧提醒） | 不需要 | **时限拆成「默认值（版本化）+ 覆盖层（运行时）」** |
| 新增执行资源绑定，希望在途实体也用 | 不需要 | 在途实体用旧版是**正确的** —— 它当时就该按旧配置跑 |
| 配置发错了，在途实体正按错的跑 | 性质不同 | 这是**数据修复**，走业务修正事件（4.4 事件分类） |

第二行是核心解法：

> 时限不该是节点配置里的硬编码数字，而应是「默认值（进版本）+ 覆盖层（运行时数据）」。需要临时调整的从来不是规则形状，而是取值。把取值从版本里拆出来，重绑定需求就从源头消失了。

第四行单独说明：归位成**业务修正事件**而非新开配置通道。理由是配置通道一旦允许"改在途实体的版本"，锁版最核心的确定性（4.6）就被打破 —— 改版瞬间会出现"部分已切、部分没切"的中间态。

> **触发重评的信号**：真的出现"某批次必须整体切到新配置"、且无法用覆盖层表达的需求。

### 6.3 域迁移 —— 是设计错误的症状

**域迁移的需求通常意味着域划错了。** 真实场景只有两类，都不需要迁移。

**场景 A：域被拆分或合并**

```
旧域 → 状态置 stopped（停止新建实体）+ 保留只读
     → 域内在途实体按各自锁版配置跑完 → 归档
新域 → 新实体进新域
```

与实体锁版同一哲学，零新机制。

**场景 B：实物流转中要跳到另一条流程**

```
实体 1（原域）  → 置 terminated（记原因）
实体 2（目标域）→ 新建，携带 ref_to = 实体 1
```

三个好处：两域留痕各自完整不被污染；"这台机为什么提前转出"一查 `ref_to` 就知；**完全绕开状态兼容性判定** —— 而那正是"迁移"这个概念最麻烦的部分。落地要求见 4.1。

> **触发重评的信号**：出现"同一实体需要在两个域之间来回"的真实需求 —— 那说明边界确实没划对，正确动作是**合并域**而不是加迁移能力。

### 6.4 契约演进 —— 唯一现在必须落一项

两条版本轴的分离见 2.2。四类变更的代价：

| 变更 | 后果 |
|---|---|
| 加可选字段 | 安全 |
| 加必填字段 | 已挂载的调用全部失败 |
| 删字段 | 历史产物里还有该字段，读取方崩 |
| **改字段语义**（形状没变，含义变了） | **最危险：版本号没变但行为变了，无机制能发现** |

第四种逼出一个纪律：**语义变更必须升契约版本号，即使 schema 形状完全没变。** 形状比对只能当辅助，版本号由人显式管理。

配套实践建议：**把字段语义写进契约**（取值范围、单位、枚举含义）。这样"改字段描述"变成一个可 review 的动作，语义变更就不会悄悄发生。

三个架构要求的理由：

1. **契约历史版本永久保留，不可删除** —— 老配置要永远能用 unlike 代码。这是硬规则，不是运维选项。
2. **配置存契约版本号 + 兼容区间声明**，编译期检查、不兼容则发布期阻断 —— 老配置永远可用，且兼容性校验复用了已有机制，不新增。
3. **产物写入时记 `produced_by: { tool, contract_version }`** —— 历史数据永远可解释。

> **第 3 条是全案唯一「现在不做，以后补不回来」的动作。** 其余（兼容区间怎么声明、语义变更怎么评审）都可以等到第一次真要改契约时再定策略 —— 但历史产物一旦产生就补记不了。

**执行资源版本不进幂等键**（2.5）—— 否则工具一升级全部重跑；但要记进运行记录。

### 6.5 并发规模 —— 拆三个量，两个不用等

| 量 | 决定什么 | 一期需要吗 |
|---|---|---|
| 在线并发用户数 | 连接层容量 | 一期要 |
| **提交峰值速率**（提交/秒） | 事务层、P0 队列深度 | 一期要，但可从运行日志算 |
| 同时处于推理态的比例 | 推理限流档位 | **推理上线后才要** |

关键观察：

> **Worker 池规模不需要实测。** P0 的定义是"前台用户在等"，一个用户最多同时等一个派发，因此 P0 并发数 ≈ 同时在提交的人数。这个量从运行日志（每条记录含 user + 时间戳）**直接可算**，不需要专门压测或等实测报告。

所以这项缩到只剩推理侧并发档位，而推理按 1.5 延后上线。**一期上线后从运行日志算提交峰值即可，不必专门做峰值测试。**

### 6.6 离线兜底 —— 难点被普遍搞错了

先纠正一个直觉：**补录的难点不是"录入"，是"不知道系统里已经有什么"。**

录入极简单（字段少、下拉多）。真正难的是状态对齐 —— 断网期间系统可能仍在被别人录入或推进，纸单说"外观已完成"，但系统里这台机可能已在下一环节。

这个观察决定解法：补录的真正需求是**状态对齐**，而状态对齐恰好是提交前置校验（4.11）已在做的事。于是三个机制（留痕要求见 4.10）：

| 机制 | 内容 | 理由 |
|---|---|---|
| **同一提交入口** | 补录走正常提交路径，不开第二个入口 | 单一真源。录入门槛低不是问题（正常路径本来就不多打字） |
| **双时间戳** | `occurred_at` + `recorded_at` | **两者差异本身就是需要核对的地方**；只记其一等于丢失信息 |
| **质量降权** | 离线数据在派生统计与 Agent 归因中显式标记 | 离线数据是照纸单重录、时刻不可信；不标记则归因带一个未声明的误差 |

状态冲突由提交前置校验**自然拦住**，不需要专门的冲突处理逻辑 —— 这是提交级校验的附带收益。

纸单**不是真源**，只是录入的来源凭证：保留编号用于追溯，不为它建第二套数据。

### 6.7 收敛成两件事

| # | 事项 | 时机 |
|---|---|---|
| **1** | **产物写入时记录契约版本号**（`produced_by`）+ 契约历史版本永久保留 | **动手前**，唯一不可延后 |
| 2 | 审批流 / 重绑定 / 域迁移 / 契约兼容区间声明 / 并发档位 / 离线兜底 | 等各自真实触发信号出现（各节已给触发条件） |
